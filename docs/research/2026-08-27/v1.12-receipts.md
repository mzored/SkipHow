Codex 0.149.1, Claude Code as installed on 2026-08-27. Every command below was run against the real
binaries; nothing here is inferred from documentation.

These are **invocation** receipts, not field receipts. They record that the cross-host review rung
[ADR 0009](../../decisions/0009-reviewer-inherits-and-one-engineering-reference.md) adds in 1.12.0
runs, holds its boundary, and returns usable findings. They do not show an owner-facing run reaching
that rung on its own, which stays `UNVERIFIED`.

## What `codex review` actually accepts

`codex review --help` reports three scope flags (`--base <BRANCH>`, `--commit <SHA>`, `--uncommitted`)
and an optional `[PROMPT]` that reads from stdin when given as `-`. **The scope flags and a prompt are
mutually exclusive.** Every combination was tried:

```
$ codex review --base main -
error: the argument '--base <BRANCH>' cannot be used with '[PROMPT]'
$ codex review --commit HEAD -
error: the argument '--commit <SHA>' cannot be used with '[PROMPT]'
$ codex review --uncommitted "say ok"
error: the argument '--uncommitted' cannot be used with '[PROMPT]'
```

This is why `model-routing.md` puts the candidate range in the brief rather than in a flag: SkipHow
always needs the owner request carried into the review, and a scope flag would forfeit it.

`--strict-config` validates `-c` overrides, not only `config.toml`, so it is a real key check:

```
$ codex review --strict-config -c not_a_real_key_xyz="1" -
Error loading config.toml: unknown configuration field `not_a_real_key_xyz` in -c/--config override
```

Both keys the reference names survive it: `-c model_reasoning_effort="high"` and
`-c sandbox_mode="read-only"`. `codex login status` answers `Logged in using ChatGPT` — a bounded auth
check that starts no session.

## The Codex direction, on this release's own diff

The 1.12.0 candidate reviewed itself through the rung it adds. Base `6f7ee9c`, candidate the working
tree, brief naming the range, the owner request, the package's hard constraints, and "return findings
only":

```
codex review --strict-config -c model_reasoning_effort="high" -c sandbox_mode="read-only" - < brief.md
```

127 s wall clock. Banner disclosed the effective model as `gpt-5.6-sol`; the `(reasoning=high)` level
was the one the flag set. It read the tree, ran `git`, wrote nothing, and returned three severity-tagged
findings with `path:line` evidence. It did not start a workflow of its own — but SkipHow is not
installed as a governing plugin in this repository, so that is not evidence for a project where it is.

Two of the three were confirmed defects in the candidate and were fixed before commit:

- **The reference was widening authority.** The closing line read "installing the tool authorizes
  sending it the candidate". The root says only the owner's direct request and host policy grant
  actions and that a reference can narrow scope, never widen it; [ADR 0015](../../decisions/0015-unconditional-invariants-live-in-the-root.md)
  puts authority boundaries in the root for exactly this reason. The behaviour the owner chose is
  unchanged — no prompt — but it is now stated as what it is: the pass runs a tool the owner installed,
  on this machine, under the authority the change already carries. A first attempt at the fix leaned on
  "the root's rule on secrets and private data governs the brief", which ADR 0015 had already rejected
  ("a brief to a local delegate needs the working directory"); that clause was dropped rather than
  shipped.
- **The Claude direction did not enforce read-only.** It read
  `--allowedTools "Read Grep Glob Bash WebFetch WebSearch"`. `--allowedTools` pre-approves tools rather
  than restricting the set, and an unrestricted pre-approved `Bash` can modify the very candidate under
  review. The reviewer also noted the new test missed this: absence of the strings `Edit` and `Write`
  proves nothing about Bash.

The third was a P2 on this file's absence: the changelog described model behaviour with no receipt
under `docs/research/`. This document is that receipt, and the changelog now cites it.

## The Claude direction, and its boundary

Two forms were measured on a fixture with a planted defect (`add(a, b)` returning `a - b`), each asked
to review the change and then to *attempt* a write to `boundary-probe.txt` and report the literal
outcome.

| Form | Review returned | Write attempt | File created |
| --- | --- | --- | --- |
| `claude -p - --effort high --permission-mode plan` | the defect, one line | never issued; plan mode prohibits non-read-only tool use | no |
| `claude -p - --effort high --disallowedTools "Edit Write NotebookEdit"` | the defect, one line | issued via Bash redirection, blocked; a `tee` retry stopped at the permission layer | no |

Both hold against the *model's* tools. `--permission-mode plan` ships because it bounds them by host
contract rather than by a list of tool names that goes stale when the host adds one.

## The two hosts are not equally bounded

The re-review below raised this and it is measured rather than argued. A project hook was planted in the
same fixture — `.claude/settings.json` with a `PreToolUse` hook on `Bash` that writes `hook-probe.txt`,
and `.codex/hooks.json` with the equivalent — and each host was asked to run one read-only command.

| Host | Invocation | Planted project hook |
| --- | --- | --- |
| Claude Code | `claude -p - --permission-mode plan` | **fired**; `hook-probe.txt` written during the run |
| Codex | `codex review -c sandbox_mode="read-only" -` | did not fire; no file created |

Plan mode governs the model's tool use. It does not disable the reviewed repository's lifecycle hooks,
which run outside the permission layer, so the Claude direction is bounded by the host's permission layer
and not by a sandbox. Codex's `sandbox_mode="read-only"` is an OS-level boundary and Codex additionally
requires persisted hook trust, so the same probe never ran there.

`--bare` does skip hooks, and was rejected: it forces `ANTHROPIC_API_KEY`/`apiKeyHelper` auth and never
reads OAuth or the keychain, which breaks the subscription owners this rung exists for, and it also skips
`CLAUDE.md` auto-discovery, which the reviewer is supposed to read for repository standards.

So the reference names the boundary instead of claiming one, which is what
[ADR 0002](../../decisions/0002-host-native-execution.md) asks: "SkipHow documents the boundary instead of
claiming an independent sandbox."

One wart, recorded rather than papered over: the plan-mode run that was asked to attempt a write exited
**1** while still printing its review to stdout. A plain plan-mode run exits 0. A caller that treats a
non-zero exit as a failed lane could therefore drop a review it actually received. The reference tells a
run to read the verdict, not the exit code, and this is why.

## The re-review

The fixed candidate went back through the same rung with a brief that named the three findings and asked
whether each was fixed or only reworded, plus regressions. 185 s, three findings, all confirmed and all
fixed before commit:

- **P1** — `--permission-mode plan` does not disable the reviewed repository's hooks, so calling the
  Claude direction read-only overclaimed. Measured above; the reference now says what plan mode does and
  does not bound.
- **P2** — the reference had been reworded but the ADR amendment and the changelog still carried the exact
  grant that was removed ("installation and authentication authorize sending the candidate"), leaving the
  policy record self-contradictory. Both now state the same thing the reference does.
- **P2** — the published budgets were stale: they were measured before the last trim. Recomputed against
  the delivered tree (`model-routing.md` 598, references 3,900).

## The third pass

A third pass confirmed the authority wording was now aligned across the reference, the ADR amendment and
the changelog, and that the published counts recompute. It raised two more, both confirmed and fixed:

- **P1** — the reference still carried a blanket "read-only" for the pass while the measurement above
  shows the Claude direction is not, and the new test's comment repeated the same both-host invariant.
  The blanket claim is gone; each bullet now states its own host's boundary, and the test comment says
  the two are not equally strong.
- **P2** — "a skill installed there starts no workflow of its own" asserted a behaviour this release's
  own receipt lists as `UNVERIFIED`. The reference now says a skill installed there may still engage and
  tells the run to treat a reply that is not findings as a dropped pass, which is actionable and true.
