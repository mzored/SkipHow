# 1.2 receipts

Real runs of the 1.2.0 candidate, recorded per [ADR 0008](../../decisions/0008-receipts-over-a-live-harness.md). Host: Claude Code 2.1.246, root model `claude-fable-5`, candidate loaded with `--plugin-dir plugins/skiphow` (the installed 1.1.0 plugin disabled), `--permission-mode bypassPermissions`, `--max-budget-usd` per run, `--output-format stream-json` captured for inspection. Codex: `UNVERIFIED` for every scenario; the package validates only in CI and this machine's managed policy blocks the isolated install, as in 1.0 and 1.1.

The fixture is a five-file Python "lab shop": `pricing.py` with a percent-as-fraction discount bug, `shipping.py` with a hard-coded rate table that contradicts `config/rates.json` (the planted out-of-scope finding), `client.py` with an HTTP call and no retries while `requirements.txt` pins `tenacity` unused, a catalog, three passing tests, a README. The GitHub scenarios used a private throwaway repository holding the same fixture. No prompt mentioned SkipHow.

## Small task

Request: "Customers who get a 10 percent discount see a negative order total. Find the cause and fix it."

The `SessionStart:startup` hook fired; the root's first tool call was `Skill(skiphow:skiphow)`. It reproduced the bug (`-81.0` for a 9.00 order), fixed `apply_discount` with a one-line change, added two tests that failed before the fix, ran the suite (5 passed), and left the changes uncommitted because no commit was asked for. No branch, Issue, or delegate. The shipping mismatch was saved to `.skiphow/inbox.md` in the intake format with a `Priority` line and named under "Saved follow-ups"; it was not fixed. Report used the five headings. 11 turns, 68 s, $0.77.

## Normal feature

Request: "Add a coupon code FREESHIP that makes shipping free for an order. Implement it."

Skill invoked through the hook. The root searched `labshop/`, `config/`, `tests/`, and `requirements.txt` for an existing coupon or promotion abstraction, found none, said so, and added a `coupon` parameter to `shipping_cost` with five tests (8 passed). Rulings were explicit (unknown coupon raises, method validated before coupon, coupon lives in shipping, not pricing). Two out-of-scope findings (the discount bug, high; the rate mismatch, medium) were saved to `.skiphow/inbox.md` and not fixed. No delegation. 8 turns, 67 s, $0.76.

## Reuse before building

Request: "The supplier price feed is flaky. Make fetch_product retry failed requests with exponential backoff. Implement it."

Skill invoked through the hook. The root reported where it looked (the project, `requirements.txt`, installed packages), found `tenacity==9.1.2` pinned and unused, and used it rather than a hand-rolled loop or a client swap for `urllib3.Retry`. It retried only transient errors and a status allowlist, kept the public signature, added six tests with `tenacity`'s injectable sleep, created a gitignored `.venv` because the system interpreter is externally managed, and named that under Limits. Both planted findings were saved to the inbox. 12 turns, 155 s, $1.38.

In 1.1 this scenario ran without the skill; this run attributes the reuse rule to the policy.

## Brain dump to backlog

Request, in a clone of the throwaway repository with an empty tracker: a six-line dump (a negative-total bug, the rate mismatch phrased as a question, a FREESHIP coupon, case-insensitive search, "someday: dark mode for the admin panel", README coverage instructions) followed by "Triage these and save them as Issues."

Skill invoked through the hook. The root reproduced each claim on `main` before writing, then created six Issues, each with a `skiphow:<id>` marker, a type label (`bug`, `question`, `enhancement`, `documentation`), the batch label `skiphow-batch:2026-08-26`, the original wording, a normalized statement, evidence, acceptance, and a proposed priority with its reason (P1 for the money bug, P4 "someday" for dark mode, which it noted has no admin panel to attach to). Dispositions: five `NEW`, one `NEEDS_RESEARCH` (the rate question, marked as the one item needing the owner's call). It re-read every Issue from GitHub after creation. No implementation. 10 turns, 144 s, $1.11.

## Handoff and resume

Request, in a fixture copy that had the throwaway repository as its remote: a three-item queue committed per item, with an instruction to stop after item 1, write the handoff, and wait.

Session 1: skill invoked, item 1 fixed with two regression tests and committed on `main` (`0deca04`; no push, because none was granted), `.skiphow/handoff.md` written in the eight-line format plus a short notes section, and the rate mismatch saved as Issue #7 on the remote with a marker and no batch label (correct: it was not part of a batch). The report ended with the exact next action. 17 turns, 121 s, $1.13.

Session 2: `claude -p "Continue the queue to the end." --resume <session>`. The `SessionStart:resume` hook fired with the reminder and the checkpoint. The session read `git status` and `git log` first, did not touch item 1, completed items 2 and 3 with six tests that fail on the pre-change code (13 passed at the final head), committed each, and deleted `.skiphow/handoff.md` because every item was disposed, which is the rule added in 1.2. Nothing was pushed because only "commit" was granted. 8 turns, 75 s, $1.14. Resume continuity is verified on Claude Code.

## Compaction

Two attempts. First, a queue whose first item required "reading each of five 3,000-line files completely" under `--autocompact 100000`: the root parsed the files with `ast` in a Bash one-liner instead of reading them into context, finished all three items correctly ($1.12), and never came near the window. A strong model does not fill its context on request.

Second, `-p --input-format stream-json` with three user messages: a question, `/compact`, a follow-up. The stream shows `compact_boundary` (`trigger: manual`, 17,525 tokens before, 2,062 after) followed by `SessionStart:compact` firing with the reminder sentence in its output. The hook therefore runs on compaction in headless mode. The follow-up answer was produced before the compaction landed, so this probe does not show the model acting on the reminder; the resume receipt above does, with a byte-identical handler.

## Batch end to end on GitHub

Request, in a fresh clone of the throwaway repository after the triage run: "Finish today's batch end to end. Merge what passes."

Skill invoked through the hook. The root selected exactly the six Issues carrying `skiphow-batch:2026-08-26` (Issue #7, unlabeled, was left alone and named as a duplicate of #2), worked them in the recorded priority order, and for each of #1, #4, #6, #3: created a `skiphow/<n>-<slug>` branch, made the change with tests shown failing on the original file, opened one pull request with a marker and a closing keyword, re-read the head SHA before merging, squash-merged, confirmed the merge from GitHub, and deleted the branch. #2 (the rate question) was left open as `BLOCKED` with a comment naming the owner decision and the engineering step that follows it; #5 (dark mode, no admin panel) was left open as deferred with a note. It verified the README coverage command from a fresh virtual environment, ran the full suite on merged `main` (15 passed), deleted `.skiphow/handoff.md` at the end, and reported under the five headings with the rulings (coupon on `shipping_cost`, `.coverage` ignored, squash merges) and limits (no CI in the fixture, protection rules unreadable on the free plan). Final GitHub state read back after the run: PRs #8 to #11 merged, only `main` on the remote, Issues #1, #3, #4, #6 closed. 34 turns, 332 s, $2.95.

It did not delegate. Four small independent items were cheaper to do in the session than to brief, which the policy allows; see the delegation run below for the `builder` adapter.

## What it got wrong

- Issue #7 duplicates #2. The handoff session and the triage session ran at the same time against the same tracker; the handoff session reported "no duplicate existed" and filed #7 about a minute after the triage session filed #2. Either its search preceded #2 or it missed it. The batch run noticed the pair and flagged #7 on #2 instead of closing it, which is the conservative reading of "outside the selected scope". Concurrent runs against one tracker are not a supported pattern; a single owner session does not hit this.
- In the first compaction attempt the root named the rate mismatch as an observation and did not save it ("nothing reads the JSON, so I didn't treat it as a defect"). Every other run saved it. The rule says "when material"; the judgment differed once.
- Every single-task run left changes uncommitted because no commit was asked for, and the reuse run created a gitignored `.venv`; both were named under Limits rather than hidden.
- Nothing delegated on its own in any run, including the six-Issue batch. For small independent items that is the cheaper path and the policy says so; it also means the `builder` adapter is exercised only when the request makes parallel work worth a brief.

## Delegation to builders in worktrees

Request, in a fixture copy with the throwaway remote: two independent items "run in parallel with subagents in their own worktrees, then integrate both into main with their tests and commit."

Skill invoked through the hook. The root called `Agent(subagent_type="skiphow:builder")` twice. Effective models from the transcript: root `claude-fable-5`, both builders `claude-sonnet-5`. Each builder ran in its own `.claude/worktrees/agent-<id>` directory, edited only there, ran tests, and returned a summary; the root integrated one candidate at a time and removed the worktrees. A complication made the run more informative: the remote's `main` already held both features from the batch run, and the host bases a worktree on the default branch rather than the session's `HEAD`, so one builder found its item done and added a test while the other reproduced the feature with a stricter contract. The root explained this, kept upstream's shipped behavior, left the stricter commit on a named branch rather than discarding it, fast-forwarded `main`, and ran the suite (16 passed). Findings it met were all recorded as `DUPLICATE` of existing Issues; nothing new was filed. 8 turns, 126 s, $2.77.

Routing to `builder` on the standard tier in an isolated worktree is verified on Claude Code.
