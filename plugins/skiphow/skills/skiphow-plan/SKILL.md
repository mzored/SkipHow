# SkipHow plan

Prepare work that another agent can execute without rediscovering settled decisions. Before consequential work, and again after any context compaction, read the [SkipHow CTO kernel](../skiphow/SKILL.md) unless its full text is already in context; a summary is not its text. It remains responsible for technical judgment and owner questions.

Explicit invocation of this skill requests a specification and planning records in the project's authorized tracker. Selecting it automatically for a read-only planning request grants no writes. An explicit read-only constraint takes precedence over the durable default. Keep implementation, commits, and delivery outside this workflow.

Use [product](../skiphow/references/product.md) to recover the intended outcome, current behavior, constraints, exclusions, and acceptance conditions. Investigate before taking genuinely unresolved product choices to the owner. Carry the interview through the questions their answers reveal until no known product choice remains open in the accepted execution scope. Preserve settled answers, keep dependent behavior undecided until its answer arrives, and prepare independent work meanwhile. Missing answers leave incomplete preparation, not an execution-ready plan; later discoveries can still require a decision during execution.

Use [technical design](../skiphow/references/technical-design.md) for consequential choices and build-versus-reuse analysis. Establish what the repository already provides before proposing new logic or dependencies. Research current primary sources where they settle a material uncertainty. Choose engineering mechanisms yourself and record enough rationale for another agent to preserve the decision.

For user-facing work, carry the relevant journey scenarios, design direction, and identified reuse constraints into the specification and tasks that depend on them. Separate accepted product decisions from proposals and engineering judgments. Preserve enough source context for an implementer to understand what must hold and why. Record the resulting decisions and acceptance conditions independently of the specialist capability that helped establish them; an executing agent reassesses the capabilities available on its host while preserving the accepted outcome.

Apply [delegation](../skiphow/references/delegation.md) to substantial independent research and to slicing. Every task recorded for execution delivers one independently verifiable outcome, cut through the layers where the work has them, that one implementation agent can carry from its record to a verified, reviewable candidate. One assignment allows normal tool calls and review corrections. A grouping record collects tasks and is never dispatched. Size every task in the accepted scope now; split one that needs several agents or defers its own split. Keep implementation and its necessary checks together when separate parts have no independently verifiable outcome. Small cohesive work stays one task. Compatible migrations and mechanical work use independently verifiable units; a large uniform automated change may stay one task when the meaningful change is bounded and completeness can be checked. A task's size is a judgment from evidence, not a promise; the executing lead reslices one that proves larger.

Where the accepted work lacks a proven path through its components, choose a thin first slice with real behavior. Establish only the structure and component connections that slice needs, verify the working path, then expand it through the remaining bounded slices. Reuse an established path in a mature project. The first working behavior preserves required safety, integrity, and compatibility. Name what its result unblocks and which later assumptions the lead must recheck at dispatch. Independent preparation can proceed before that result; prepare the whole accepted task set without inventing a universal foundation stage.

Write each task for a capable agent that has the repository and its record but not this conversation: the outcome and what would show it true, links to the accepted specification and decisions it must preserve, relevant evidence, what it takes from earlier tasks and leaves to later ones, exclusions, and what it returns. Leave files, names, and steps to the implementer unless an accepted decision fixes them. Show actual blocking results, available parallel work, and shared writes, runtime resources, or integration capacity that constrain dispatch. Consuming the same settled API creates no dependency by itself. Name any earlier result that could change a later task and what to recheck at dispatch. Keep open product decisions explicit. Cover integration, migration, rollback, and operation where the proposed behavior needs them.

Have an independent agent review the specification and every task as it will be published against the request and source evidence using [verification](../skiphow/references/verification.md). Check missing outcomes, conflicting decisions, and verifiable acceptance. A shared outcome alone does not establish one-agent feasibility: assess required context, materially different changes, manual implementation, verification, review, and integration together. Where workload is materially uncertain, use existing measurements, comparable completed work, or representative source and check inspection; a full inventory is not required. A size finding names the concrete load and a smaller independently verifiable cut that preserves all acceptance and dependencies. Split where reliability and total cost improve, accounting for repeated context, coordination, and integration; file, line, or acceptance counts are no universal limit. Across tasks check invented or missing dependencies, overlaps, uncovered outcomes, unnecessary prescription while retaining justified contracts and reuse constraints, and bounded review and integration workload. Check the journey's application context and the authority behind consequential product choices. Resolve supported findings before finalizing. If independent review is unavailable, finish preparation and report review as unverified.

Use [tracked work](../skiphow/references/tracked-work.md) to reconcile existing records and save the plan when authorized. Use GitHub Issues within the established audience unless the project uses another authorized tracker. Write engineering artifacts in English. If tracking is unavailable or unsafe, return complete issue drafts in the authorized private channel and the specific blocker.

Return the specification and issue links or drafts, material decisions, review evidence, unresolved limits, and whether the scope is ready for execution. For ready scope, use this launch shape with the target host's explicit skill invocation syntax. Default to longrun; preserve a different execution workflow the owner already selected.

```text
$skiphow-longrun
Deliver the accepted implementation scope in <plan-reference> to <agreed-destination>.
```

Replace placeholders with concrete accepted records and the agreed destination. Add only otherwise-missing project location, accepted subset, or necessary run constraints, preserving their authorization provenance. Requirements and dependencies stay in the task records; execution policy stays in SkipHow. Grant no new protected actions. Keep unfinished preparation, inaccessible sources, and known human prerequisites explicit as blockers to the affected scope; a saved plan proves neither readiness nor permission. Stop before implementation.
