# Product acceptance

Product acceptance checks that changed user-facing semantics deliver the approved Product Contract. It is SkipHow's implementation of an intent and authority check, not a universal engineering phase. It is required only for user-visible work governed by a Product Contract. It is not Owner QA and it does not reopen technical decisions.

Before delivery, the Product Director records the acceptance scenarios that matter to the contract. Include the main journey and any material alternative, empty, error, or recovery state. State the evidence that can show each scenario, such as a working runtime flow, rendered output, API response, or accessibility result.

After the CTO has verified the delivered state, the Product Director compares the affected scenarios and their evidence with the Product Contract. Record the contract revision, delivered-state identity, evidence location, reviewer, date, and `accepted` or `returned`. The identity may be a Git commit, working tree, deployment, generated artifact, or repository-defined equivalent. A behavior-preserving later delta may instead use the `carried-forward` status defined below.

Acceptance evidence is invalidated by changed product semantics, not by state identity alone. After a correction, repeat only acceptance scenarios whose user-visible behavior or evidence changed. CI configuration, metadata, test harness changes, parser internals, validators, and behavior-preserving refactors do not require another Product Director pass when the previously accepted product evidence still applies. In that case, create a final-state `carried-forward` receipt that links the prior acceptance receipt, identifies the reviewed delta, and records why no contract scenario or product evidence was invalidated. Any delta that changes the user journey, output, error state, accessibility behavior, or another contract-visible result requires Product Director acceptance for the affected scenarios in the new delivered state.

For normal `EXECUTE` delivery, store the receipt at the repository's established evidence location. When the repository has no convention, use `.skiphow/evidence/product-acceptance/<state-identity>/<contract-id>.json`; this is an evidence artifact, not a durable campaign. For `cto-run`, use the campaign receipt location from the durable state contract. A carried-forward receipt records the Product Contract revision, new delivered-state identity, prior receipt, reviewed delta, evidence location, reviewer, timestamp, and `carried-forward` status.

Return only concrete mismatches between the delivered state and the contract. The CTO corrects them and submits a new final state. If the desired behavior itself must change, return to `shape` for a Product Contract decision. Ask the Owner only when that decision needs Owner authority.
